# P2C INTEGRATE v2 — inverting the STAR integration

> Plan for the "see how far we can take it" investment. Supersedes the INTEGRATE-1/2/3 hook
> contract. Evidence base: `bench/PHASE2C-integrate-1.md` rounds 1–4.

**Goal:** STAR CPU-s per sample ≤ −12% vs stock (memo-grade ≥ −8%), byte-identical output, with
the seed search served in place from the resident index on the GPU.

**Architecture:** Stop *hooking* STAR's per-read loop and start *restructuring* it per chunk:
one pass that does STAR's own per-read prep exactly once and emits seed requests as a side
effect; one GPU batch per chunk-slice; one pass that maps reads consuming results positionally.
Then move work the CPU still does (prefix lookup, chain continuations) onto the device.

**Where the last four rounds leave the accounting (20M, 20 thr):** stock 753 CPU-s; GPU arm
mapping-phase 856 (+13.7%). Hook floor +49 (bypass arm), coordinator+consumption +54, GPU credit
unmeasured directly. Two of my last three CPU-s estimates were wrong (item 1 by 5×, item 2
entirely). **Every task below therefore starts from a measured symbol-level delta, not an
estimate.**

---

## Task 0 — paired perf differential (measurement only, gates everything)

**Objective:** measure the GPU credit and each overhead bucket directly, symbol by symbol.

- Same 4M-read slice, same box, one run each: stock; bypass; GPU. `perf record -F 499 -g`
  per arm, `perf report --no-children --sort sym` to TSV; a script diffs self-time per
  symbol × total CPU-s of the arm → CPU-s per symbol per arm.
- Outputs: `bench/evidence/integrate-v2-perf/{stock,bypass,gpu}.sym.tsv`, `diff.md`.
- What it must answer:
  1. **GPU credit:** CPU-s drop in `maxMappableLength2strands` + `compareSeqToGenome` +
     inner-search symbols, stock → GPU. Arithmetic says 39% × 0.96 × 0.764 ≈ 28% of stock
     ≈ 210 CPU-s. If measured < 120, the kernel's 6.6× does not translate to STAR's
     in-situ cost per gather (cache effects) and the ceiling drops — say so and re-plan.
  2. **Overhead buckets, measured:** `prepare_window`, `readLoad` (2nd copy),
     `qualitySplit` (2nd), prefix (`SAindex` walk, 2nd), `submit_window`, coordinator,
     `lookup`/hash, `malloc`/`memcpy`.
- Decision gate: proceed to Tasks 1–2 only if credit ≥ 150 CPU-s **and** sum of removable
  buckets ≥ credit − 60 (i.e. a ≥ −8% outcome is arithmetically reachable from T1+T2 alone
  or T1+T2+T3).

Owner: orchestrator (10 min on the Spark, under the lock). No worker.

## Task 1 — positional consumption (kill the hash)

**Objective:** replace hash-bucket lookup + full-key compare with a dense per-read candidate
array and a cursor; the identity key becomes an assertion, not a search.

- The window enumerates a read's initial-start candidates in a deterministic order
  (`piece, dir, istart`); `mapOneRead` visits them in the same order. So the k-th `lookup`
  for read *r* is candidate *k*: `frame.results[k]`. Verify the key matches (cheap compare);
  on mismatch → CPU fallback + counter (`positional_miss`), never a search.
- Coordinator: batches are contiguous slices of the chunk's dense request array; drain
  writes results back at the same index. No `unordered_multimap`, no per-frame allocation.
- Tests: existing coordinator suite; new: 1,000-read synthetic with shuffled candidate
  completion order asserting every consumed result lands on its own candidate; strict
  oracle unchanged.
- Expected removal (T0 will size it): `submit_window`, `lookup` hash, `malloc`. Order of
  20–50 CPU-s.
- Owner: Terra. Files: `star_integrate.cpp/.hpp`, `star_integrate_window.cpp`, tests.

## Task 2 — full frame hand-off (STAR's prep runs once)

**Objective:** `oneRead` for a read with a frame does **no** `readLoad`, no combine, no
`qualitySplit`: names, quals, `readLength*`, `readLengthOriginal`, `clipMates` state,
`Read1[0..2]`, `Nsplit`/`splitR` all come from the frame. Round 4 did `Read1` (14 CPU-s);
this does the rest.

- Stream handling: the window already reads the chunk's stream ahead; `oneRead` on a hit must
  advance the stream past the read without parsing (the frame stores the byte span). On a
  miss, stock path from the stored stream position.
- `readFilter`, `readFilesIndex`, `iReadAll`, `readNameExtra` are STAR-side state that
  `readLoad` sets: enumerate every out-parameter of `readLoad` (`readLoad.cpp:4-6`) and
  every field `oneRead` sets before `mapOneRead` (`ReadAlign_oneRead.cpp:14-75`); each one
  is either copied from the frame or proven unused downstream — a checklist in `CONTRACT.md`.
- `qualitySplit` result (`Nsplit`, `splitR[3][]`) is stored by the window (it already
  computes it) and copied in.
- Parity is the proof (names/quals/flags in SAM cover every field). Unit test: 1,000 random
  paired reads with random clips/filters, frame path vs stock path, all fields equal.
- Expected removal: 2nd `readLoad` + `qualitySplit` + combine. T0 sizes it.
- Owner: Terra (or Astra if T0 shows `readLoad` side-effects are subtle). Files:
  `make_star_integrate.py` (the `oneRead` hook grows), `star_integrate_window.cpp`,
  `CONTRACT.md`, tests.

**Gate after T1+T2:** gate (i) + 3-repeat timing (rounds 5). Predicted: bypass floor → ~+2%,
GPU arm → between −5% and −10%. If ≥ −8%: PIPELINE-RUN is funded at that point; continue
anyway.

## Task 3 — prefix lookup on the device

**Objective:** the GPU does the outer search too: `SAindex` walk from the read's `Lind`-mer
to `(iSA1, iSA2, L_in)`, then the inner search, per request. The CPU sends
`(read bytes, S, N, dirR)` only.

- `SAindex` is resident (part of the 30 GB); the walk is a few dependent loads per request,
  divergent but small next to the inner gathers. Kernel extension in
  `crates/umgpu/shim/seed_probe.cu`; strict oracle compares all four outputs against the
  stock function (which does its own prefix) — unchanged proof.
- Removes the window's `append_prefix_call` CPU cost (T0 sizes it; round-2 profile said
  ~70 CPU-s with the caveat that profile overestimated item 1).
- Owner: **Astra** (kernel correctness at the SAindex boundary — sparse `SAiMarkNbit`,
  `SAiMarkAbsentBit`, `genomeSAindexNbases`, all per `Genome_insertSequences`/`SuffixArrayFuns`).
- Gate: round 6.

## Task 4 — chain continuations on the device (the remaining 24% of gathers)

**Objective:** serve `Lmapped > 0` searches. A continuation's `Shift` depends on the previous
result's `L`, so per chunk-slice: round *k* results → round *k+1* requests, until no read
has an open chain. CHAIN-POSITION measured ~3–4 rounds typical.

- Coordinator runs rounds within a slice before pass 2 begins; per-read chain state
  (`Lmapped`, `flagDirMap`) lives in the frame. STAR's `mapOneRead` then consumes *every*
  seed positionally; `maxMappableLength2strands` becomes a pure consumer on the hot path.
- Parity risk: `flagDirMap` short-circuit (`ReadAlign_mapOneRead.cpp:60-62`) and the
  `seedSearchLmax` branch must be reproduced exactly in the request generator; the strict
  oracle catches any drift.
- Owner: Astra (design + generator), Terra (coordinator rounds).
- Gate: round 7. Ceiling with T1–T4 at 96% coverage: ≈ −30% STAR CPU-s (39% × 0.96 × 0.998
  minus residual overhead).

## Task 5 — resident-to-resident identity (housekeeping, any time)

Bind the index identity by sampling STAR's loaded arrays against the USI context's, no file
reads. Removes ~70 s startup wall and ~42 `sys` CPU-s per run. Terra, small, do it alongside
T1.

```
T0 (orchestrator, today) ─► decision gate
T1 + T5 (Terra)  ──┐
T2 (Terra/Astra) ──┴─► round 5 gate+timing ─► Astra review of the two-pass contract
T3 (Astra)          ─► round 6
T4 (Astra + Terra)  ─► round 7 ─► PIPELINE-RUN if ≥ −8%
```

One worker per file set, one Astra review after round 5 (the two-pass contract is where
STAR semantics can drift silently: chunk boundaries, `clipChunk`, `readFilter`, EOF handling).

## Odds (honest)

- T0 shows credit ≥ 150 CPU-s: **70%** (the arithmetic is sound; the risk is in-situ cost
  per gather being lower than the probe's).
- T1+T2 reach ≤ −8%: **40%**. With T3: **60%**. With T4: **70%**. Reaching −12% at all: ~55%.
- Parity holds through T2 (full hand-off): 85%; through T4: 70% (continuation generator).

## What this is not

Not a memory experiment anymore — that part is answered. This is "can STAR's read loop be
restructured around a batch seed oracle without changing a byte of output." If it can, it
generalizes (any aligner with a resident index); if T0 says no, the memo says so with numbers.

## Task 0 result (measured, 4M slice, 3 arms, perf -F 499; `bench/evidence/integrate-v2-perf/`)

| arm | user+sys CPU-s | of which identity setup | mapping-phase |
|---|---|---|---|
| stock | 160 | — | 160 |
| bypass | 172 | — | 172 (+7.0%) |
| gpu | 271 | ~94 (SHA `libcrypto` 40 + smmu/copy/spinlock ~54) | **~177 (+10%)** |

**Setup is 94 CPU-s per run at any input size** — 12% of a 20M stock run on its own. Rounds
1–4's "+42 sys" undercounted it (the SHA is user time). T5 is therefore not housekeeping; it
is the single largest fixed cost and moves first.

**GPU credit, measured directly:** seed-search bucket (`compareSeqToGenome` +
`maxMappableLength2strands` + `maxMappableLength` + `binarySearch2`) stock **56.0** → gpu
**27.3**: credit **28.8 CPU-s = 18% of stock**. Seed search is 35.0% of STAR's in-situ CPU
(lane's 39% held up). But the GPU removes only 51% of the bucket, not the 73% coverage
arithmetic predicted:
- `maxMappableLength2strands` self 8.8 → 8.0: the outer/prefix work is untouched (T3).
- `compareSeqToGenome` residual 17.6 for the ~27% of gathers not served (continuations 24%
  + misses + suppressed): proportional; T4's prize.
- coverage on this slice 86.6% (startup); at 20M it is 96% → credit ≈ 20% of stock.

**Overheads, measured:** integration self **19.5** (`lookup` alone **9.5** — the hash +
multimap + key compare, ~600 cycles per call; `prepare_window` **2.8**; `submit_window` 2.3;
rest < 1 each). Read-prep symbols stock 5.1 → gpu 5.9. Downstream (stitch/extend/transcript)
44.3 → 46.3, unchanged within noise — no behavioural drift.

**Bypass floor +12 CPU-s** is mostly `compareSeqToGenome` 44.3 → 50.0: the `compared()`
accounting patched into the hot loop (`make_star_integrate.py:34-36`) costs ~6 CPU-s even
"compiled out". The rest is `set_chain`/`inner_call` on the disabled path.

### What this changes

- **T2 (full frame hand-off) is withdrawn.** The lookahead costs 2.8 CPU-s at 4M (~13 at 20M),
  not ~70. Round 2's profile attributed the window's *first* conversion to it. Removing the
  second copy already happened (round 4, 14 CPU-s) and there is nothing left worth a card.
- **T1 (positional consumption) is worth ~12** (`lookup` 9.5 + `submit_window` + hash), not
  20–50. Still the best cheap item.
- **The bypass floor is a real, separate item:** remove `compared()` from the hot loop
  (count at the call site from `N−L`, not inside `compareSeqToGenome`), gate `set_chain`
  behind `enabled` at the generated site. Worth ~10.
- **T3 and T4 are the prize, not the polish.** With T1 + floor + T5 the mapping phase lands at
  ~−3% (155 vs 160). T3 (prefix on device, `maxMappableLength2strands` self 8 → ~1) reaches
  ~−8%. **T4 (continuations) is what gets to −12% and beyond** — residual
  `compareSeqToGenome` 17.6 → ~4 puts the mapping phase near −16%.

### Revised sequence

```
Terra now:  T5 (setup resident-to-resident, no file reads, ≤ 5 s)
            + T1 (positional consumption)
            + floor (compared() out of the hot loop, disabled-path gating)
Astra now:  T3 design + kernel (SAindex walk on device; SAi is already in the USI resident
            image — crates/umgpu/ffi/star_integrate.rs:153,652)
            ─► round 5 gate + timing when both land
Astra next: T4 (continuation rounds) ─► round 6 ─► PIPELINE-RUN if ≥ −8%
```

Revised odds: −8% after round 5: **55%**; −12% after round 6 (T4): **60%**; parity through
T4: 70%. The credit ceiling with everything on the device ≈ 35% × 0.998 ≈ −33% before
overheads; realistic floor of overheads ~10 CPU-s ⇒ **−25% is the honest best case.**
