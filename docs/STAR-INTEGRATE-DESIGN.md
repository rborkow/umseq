This object is reused across input chunks; it is not one object per read. `ReadAlignChunk_processChunks.cpp:227–249` assigns chunk numbers and calls `mapChunk`; `ReadAlignChunk_mapChunk.cpp:7–35` clips the chunk, resets worker statistics, rewinds streams and repeatedly calls `RA->oneRead()`. It increments `iRead` after completion. Output buffering and SJ collapse follow each completed read, and ordered SAM chunk publication follows completion (`mapChunk:22–26,48–65,113–122`; `processChunks:249–272`).

PE `Lread = length[0]+length[1]+1`. **`Read1[1]` is the position-wise complement of the combined sequence**, while `Read1[2]` is its reverse complement. Neither the GPU's s1 nor STAR's comparator should be given `Read1[2]`. Names, qualities, clipping and mate metadata remain live for output.

## (a) Speculate all initial starts, both read directions

Concrete mechanism: within a bounded window of reads from an already assigned chunk, prepare exact stock numeric bytes and splits; enumerate every loop-eligible `(ip,istart,iDir,Lmapped=0)`; run the **same CPU prefix/branch preparation** and retain only inner requests for GPU. Short/direct branches stay CPU. Cache the inner tuple results without calling `storeAligns`. Then run each original read through the stock scheduler in its existing worker and input order: on exact tuple match consume a result; otherwise call the original CPU function. Invoke `storeAligns` exactly once at its original call site. Discard speculative results never consumed, including suppressed reverse starts.

This is initial-frontier lookahead, not a proof that every eventual start is independent. It batches the known first requests; later `Lmapped` steps fall back. A more ambitious version can advance every independent `(ip,istart,iDir)` chain in rounds with its own Lmapped, producing a complete search trace before CPU consumption. That computes the possibly suppressed reverse chain unnecessarily and needs dependency rounds; it still may not insert seeds out of order. Do not implement that extension in the first experiment.

The complete tuple contains S/N/L_in/interval/direction. Nstart enumeration alone does not supply its SAindex work or branch choice. A read can have zero eligible inner starts, so “eight requests per read” is a capacity example, not a queue invariant.

**Work example, not observed waste distribution.** For two clean 75-base fragments, Lread=151, A=50, Nstart=2, Lstart=37. Each fragment has forward starts b,b+37 and reverse starts b+74,b+37, with N=75,38 in each direction. There are eight outer candidates per pair with total N=452. If the b=0 fragment's first forward result has L=75, its reverse initial request is unused: one of eight candidates (12.5%), but **75/452=16.59% of candidate query extent**. The second fragment begins at b=76, so full L=75 does not satisfy `Shift+L==75`. If the skipped candidate were short/direct it would waste no GPU search. If it were inner, its actual wasted work is its measured comparisons/gathers/bytes, not 75 bytes. Perfect matches and repetitive candidates have quite different search work.

For initial-frontier speculation with default unlimited mode, the only source skip within otherwise eligible starts is reverse istart=0; at most one such initial outer candidate per split is suppressed. This bounds the count after enforcing loop eligibility; it does not bound a small work fraction, since the skipped requests may contain most of the comparisons. GPU inner waste is at most all submitted work, and can be zero. The observed 93.6% inner share and 66.78 bytes/inner call cannot be assigned to skipped candidates without a conditional measurement.

Initial N=38/75 peaks suggest this mechanism is worth evaluating, but 76.49% is **not** its empirical hit rate. N=38 may be an adaptive remainder, and fragments can have other lengths and starts. Conversely an initial request need not have either N. Pending capture needs outer chain identity, first-versus-adaptive position and outcome to resolve this.

Costs included in an integration comparison: preparation of extra candidates and prefixes, materializing requests/read bytes, GPU search of used and unused candidates, synchronization, table lookup at every actual inner call, and stock CPU misses. Reusing read bytes once per window is essential; avoid copying a whole read per request. Separately report discarded candidate comparison bytes/gathers, query-extent sum, main and range iterations. Do not treat speculative N sums as physical DRAM traffic.

## (b) Yield per-read seeding continuations across a chunk

A real continuation design would split `oneRead` into preparation, resumable seeding and ordered completion. A yield is immediately before the normal inner call at `maxMappableLength2strands:96`, **after** CPU prefix preparation and **before** `storeAligns`. Resume injects L/range/count into the same lexical continuation, performs the sparse winner/store phase, updates flagDirMap and Lmapped and runs CPU work until the next inner request or end of seeding. Short/direct paths need not yield. Do not suspend inside binary search: that exports its dependent gather latency back to the CPU.

At each yield retain:

- Owning worker/chunk and stable read ordinal/generation; complete prepared sequence/complement and split array; original names, qualities, mate lengths, clipping/filter metadata and other readLoad outputs. Pointers in trInit must refer to stable per-read storage.
- Program-counter/savepoint plus ip, Nstart, Lstart, iDir, istart, flagDirMap, Lmapped, Shift, seedLength, current sparse iDist and pending S/N/L_in/low/high. Sparse1 collapses the iDist arrays; a future sparse implementation must retain NrepAll, ranges, maxLall and maxLbest until the winner loop.
- Each read's seeding state: PC and nP, nA/nUM, storedLmin, uniq/mult length/count bookkeeping, mapMarker/reset state and initial transcript metadata. The simplest correctness baseline retains all mutable ReadAlign state, but the practical design must explicitly separate seeding state from downstream alignment scratch.
- Pending/result ownership, exactly-once resume marker and admission/completion state. C++ stack locals, a shallow `ReadAlign` copy, or a pointer back into an overwritten chunk stream are not a continuation.

What becomes concurrent is **many logical reads' preparation and seeding state**, not merely GPU calls from 20 threads. Twenty workers each blocking on one request provide at most 20 pending queries. At 64k target this is 3,200× too few. The scheduler must fill a window of approximately 64k ready inner continuations (potentially more reads, because some do not reach inner), aggregate across workers, or admit fresh reads as older ones wait. A 256k frontier needs approximately 256k independently suspended reads with one outstanding request each. Submission is by a coordinator; owning CPU workers execute ready continuations or ordered completed-read work, not block individually in the C ABI. When no independent work remains, submit the partial batch or finish on CPU; never wait forever for the target.

Keep roughly 20 full downstream workspaces: winBin, WA/WC, transcript arrays, stitch scratch, output/SJ streams, transcriptome/Solo state and RNG remain on their original worker. Finish reads in original worker order, restoring seeding state into that worker's workspace before `stitchPieces`, multimapper selection and output. Later reads may finish seeding early but must not consume RNG draws, output buffers or SJ side effects early. `ReadAlign.cpp:11` seeds RNG with `runRNGseed*(iChunk+1)` where constructor iChunk identifies the worker; changing worker assignment changes the stream. Preserve assignment as well as order, or separately establish strict parity for the scheduling policy. Retaining chunk publication order alone does not prove RNG parity.

Costs are material. `ReadAlign.cpp:21–59` allocates genome-sized window bins, 10,000 windows and 10,000 transcripts by default. Creating 64k such objects is not credible. Even just the default 1,000-entry PC array, eight 64-bit words each (`IncludeDefine.h:189,239`), is **64,000 bytes/read**, or **3.815 GiB at 64k reads**. A compact continuation should retain only used PC entries while enforcing stock caps; if k seeds are live, its PC cost is `64 × k` bytes/read, plus metadata. Exact total depends on measured nP and sizeof structures; no measured continuation RSS exists. Copying fixed-capacity arrays at every yield could erase a search win.

Chunk storage also persists until all users complete. Default input capacity is 30 MB across mates and output capacity 50 MB per worker (`Parameters.cpp:1160–1162`, `parametersDefault:232`), roughly 1.6 GB for 20 workers before alignment workspaces. Window admission cannot overwrite/refill a chunk still referenced by a continuation. Copy compact prepared reads or pin chunk buffers; account for the retained capacity, head-of-line completed-read queue and EOF tails. Clipping can have chunk-level state (`mapChunk:9`), so independently re-parsing bytes must reproduce stock preparation.

Source-order consumption preserves PC deduplication, seed caps, best-seed choices and resulting windows. Applying GPU completions directly to a shared PC would corrupt both ownership and ordering. Batching can reorder pure search execution, never these effects. This mechanism avoids speculative searches but pays continuation storage, save/restore, dependency rounds, queue latency and reduced tail batches. Prefer it only if captured adaptive work is substantial enough to fund those costs.

## (c) Fixed `(read,S,dirR)` grid plus exact CPU fallback

Concrete grid example: for each split, include offsets 0,20,40,60… from its left edge for forward requests and the same offsets from its right edge for reverse requests, while remaining N>seedMapMin. This is a read-position grid; it must use stock prefix narrowing, not the probe's synthetic full-SA interval setup. Precompute pure inner results, consume them on exact match, and CPU-fallback on any missing/mismatched entry. The initial-start set from (a) can be included as extra positions; grid20 alone misses the 37-base start in a clean 75-base fragment.

The safe **exact memoization key** is `(index_epoch, read_generation, s0/s1 identity and length, S, N, dirR, L_in, i1, i2, branch/tag)`. Read identity is a stable unique token tied to immutable bytes, not a hash without collision checking. `iFrag` affects storeAligns rather than the pure search result; retain it in the CPU consumer or include it in a full outer-result key. Distinct transformed/merged/WASP reads must not share an identity. Sparse offsets and fixed-versus-adaptive calls must either generate distinct exact tuples or be bypassed.

A smaller `(read,S,dirR)` key can be proved sufficient **only within the admitted sparse1, unlimited adaptive path and fixed immutable read/index settings**: qualitySplit determines the unique containing split `(b,f)`; forward N=b+f-S, reverse N=S-b+1; sparse offset is zero. CPU prefix preparation derives Lind, branch, low/high and L_in uniquely from those bytes, N and SAindex. Thus these fields can be omitted from lookup under that proof but should still be checked against the prepared tuple initially. Enabling the fixed-length extra call (`seedSearchLmax>0`, disabled by default) breaks the N proof; so do stale read versions and changed indexes. Identical S/dir with different N or intervals can return different maximal lengths/ranges. Dropping those fields without the proof is an unsafe cache, not exact memoization.

Dense default-domain coverage removes positional misses for these initial read versions, but wastes work at unvisited positions, and remaps/rejections still fall back. Grid20 has initial N values 75,55,35,15; under this clean-fragment example it misses N38 initial searches. Do not extrapolate a 1/20 hit probability or use the marginal N38/75 frequency as a fallback rate. Real hits depend on fragment edges, accumulated L and direction. The actual fallback rate is **unknown**; without joint data, 0–100% is the only general rate bound. Even exact captured hit counts would not measure the cost of unvisited candidates: those require generating and measuring the proposed candidate set.

Evaluate work coverage, not only request coverage. Let U be the stock CPU cost of requests satisfied by the table, F the stock CPU cost of misses, G the GPU cost of **all** generated candidates, and H the CPU preparation/materialization/lookup plus batching costs on the same time basis. The mechanism wins that boundary only if `G+H < U`; total boundary cost is `G+H+F`. CPU-s and wall time need separate versions of this accounting; do not add GPU wall to total CPU-s or multiply overlapping wall stages blindly. Request hit rate cannot substitute for U, because low-cost calls can dominate counts while expensive tails dominate time.

## Batch and latency budget

Use thread-per-request. It beat warp at every measured batch; there is no evidence that warp helps the shorter real searches. The smallest measured full GPU batch is **64,000**, about 1.24 ms synthetic wall; 256k about 4.60 ms; 1M about 17.60 ms. These are targets to test on real requests, not a proven minimum profitable batch. No tiny-batch GPU performance has been established. Start with 64k target and bounded admission, compare 256k if chunk capacity permits, and use CPU for underfilled latency-sensitive tails unless real measurements justify their launch. A fill-time limit should be selected from observed CPU work saved and queue latency, not an invented microsecond threshold.

For (a), eight outer candidates/pair would require 8,000 pairs for 64k or 32,000 for 256k **if every candidate were inner**. Actual branch mix and splits change those values. A global coordinator can aggregate several workers' windows; preserve original worker ownership on consumption. With approximately 75+75 prepared pairs, two combined numeric arrays require 302 bytes/pair, or 2.416 MB for 8,000, excluding names/qualities/splits. Existing 80-byte requests + 40-byte outputs + 48-byte probe stats require 10.752 MB at 64k, 43.008 MB at 256k, excluding read arena, lookup entries, staging duplicates and page rounding. The proposed ABI adds an epoch argument, not extra per-request bytes.

At the synthetic 1M per-request rates, nominal CPU20-minus-GPU wall budget is about 10.36 ms/64k or 41.42 ms/256k. Those scaled budgets exclude speculation and every STAR integration cost and must not be carried to the much shorter real workload. At a real 5× speedup, only 80% of the *covered stock boundary time* is nominally available to fund added costs; at 2× it is 50%, before discarded work. The appropriate end-to-end boundary begins with admission/preparation of a window and ends after its stock consumers and CPU misses complete. Report separately index startup, CPU U+S, batch fill delay, prefix/candidate CPU, materialization/lookup CPU, GPU event and call wall, wait, CPU fallback and downstream STAR work.

| STAR + private inner backend, omit duplicate SAindex | 54.7591 GiB | 31.1480 GiB | ~23.6113 GiB |
| Single G/SA via umem, one CPU SAindex | 28.1087 GiB | 4.4976 GiB | ~23.6113 GiB |

Genome=3.0393 GiB, SA=23.6111 GiB, SAindex=1.4583 GiB. The inner GPU needs only Genome and SA; STAR needs SAindex to prepare prefix-narrowed requests. Current `ProbeResident` retains all three arrays for loader/provenance validation, even though `umgpu_seed_probe` takes no SAindex. Omitting its duplicate is a proposed private-loader change, not an existing facility. It saves 1.4583 GiB, not half the index. Hash/metadata validation can stream SAindex instead of retaining a second copy.

**Reservation accounting:** the 32 GiB HugeTLB pool is already reserved, leaving approximately 89 GiB general memory on the stated approximately 121 GiB machine. Allocating a 23.6113 GiB SA from that pool does not subtract it again from the 89 GiB. It leaves about 8.3887 GiB free *inside the pool*, unavailable to ordinary allocations while reserved. Under the reduced-duplicate layout the general index uses ~31.148 GiB, leaving ~57.852 GiB general for STAR workspaces, chunks, OS and file cache. Whole physical accounting is `32 GiB reserved pool + general allocations`, not `32 + all logical allocations`. vLLM is already stopped by the user; no service action is proposed.

**Peak startup:** accepting duplication retains both G/SA copies throughout mapping so CPU fallback remains independent. Minimum steady anonymous index use is the table value; startup can also retain reclaimable file cache (up to roughly one disk index), buffers and metadata. The existing `Allocation::Anon {huge:true,require_huge:true}` path attempts THP before HugeTLB (`umem/src/backing.rs:70–90`). A touched failed SA THP attempt can temporarily add ~23.611 GiB to general use; it is dropped before the HugeTLB fallback, not an additional persistent SA. With the reduced-duplicate arrangement and all other arrays already live, general index-related peak can approach **54.759 GiB** during that attempt, before file cache/workspace. Loading the GPU SA directly with the existing `Allocation::Hugetlb` option would avoid that trial, but is a future placement choice. The probe's 62.58 s load/validate figure is not a measured integrated startup time. Do not create a full-size temporary byte vector before copying into umem.

Load the two snapshots from the same immutable index epoch; sequential streaming loads avoid a third owned array. Once loaded and compared, a duplicate backend's CPU fallback reads STAR's own arrays. Failure to initialize huge-backed GPU arrays leaves stock STAR running; failure after a successful GPU launch invalidates its output until completion/error is handled. Verified huge coverage is essential given the 4K control, not just a “huge requested” flag. The accepted probe used SA HugeTLB and Genome/SAindex THP with 100% reported primary coverage, identical CPU/GPU pointers and ATS without host registration. Recheck actual allocation coverage and identity when eventually integrating; do not infer STAR's separate new[] allocation has that placement.

**Alternative private allocator patch:** in STAR/`Genome_genomeLoad.cpp:286–295`, the no-insertion, NoSharedMemory branch allocates `G1` and `SA`, then SAi; `:307–325` sets `G=G1+200`, reads Genome directly and writes sentinel 5 padding. Replace only the private G1/SA allocations with context-owned writable umem buffers; retain stock streaming reads, packed lengths/tail initialization, then freeze after all allowed loading finishes. SAi can remain STAR-owned ordinary CPU memory. `PackedArray::pointArray` attaches a non-owning pointer but does **not** clear `arrayAllocated`; a fresh non-owning PackedArray and explicit ownership tag are required. Do not allocate and then repoint an owning array.

This cannot be only a loader edit. `Genome.cpp:32–45::freeMemory` calls `delete[] G1`, `SA.deallocateArray`, `SApass2.deallocateArray`, and `SAi.deallocateArray`; its destructor block is commented out. `PackedArray.cpp:44–51` deletes only when arrayAllocated is true. Add a private ownership branch and idempotent context release at every free path; no delete[] of an mmap pointer, no separate freeing of alias views. Drain outstanding device use before clearing views/releasing the owning context. STAR's CPU readers must be bounded by context lifetime, including fallback and any Genome aliases. On initialization failure either fully roll back views and use stock allocation/loading, or keep completed owned CPU-readable buffers in CPU-only mode; never leave mixed partial ownership.

There is no safe public arbitrary-pointer import/CPU-sharing handle today. `umem` exposes `Buf<Rw>::allocate/as_mut_slice`, `freeze -> Buf<Ro>`, consuming `Buf::lease -> GpuLease`, `Submission::wait/try_wait`, and Arena. Its read-only type is an ownership contract, not automatic enforcement of C++ aliases. A private bridge must confine unsafe immutable CPU views to live read-only ownership, as the current probe's scoped callback does. General `Submission` retains leases and quarantines on uncertain completion; preserve this principle if GPU use is asynchronous. Do not claim a new owned-session API already exists or restart the held owned-session card to make this design work.

With single storage, startup general pressure from a THP SA trial is at most roughly the single total 28.1087 GiB plus non-index costs; direct HugeTLB allocation avoids the trial. Steady index allocations drop by **26.6504 GiB** relative to the reduced-duplicate option. This patch becomes worth its risk if real speed and integration coverage are convincing and measured memory/startup pressure limits useful concurrency. First accepting duplicate storage isolates scheduler correctness from allocator/free-path changes and fits the stated budget conditionally on measured non-index use. Merely saving memory before a positive real-request decision does not justify the ownership patch.

**Index mutability:** v1 admits only the pinned static Full index, sparse1, no transform and no mapping-time sequence/SJ insertion, with twopass None and no active SJ-save/insertion path. Prebuilt annotated SJ bytes are part of the immutable index, not an unsupported mutation. `sjdbInsertSave Basic` appears in saved generation parameters; the guard must examine actual insertion/twopass flags rather than rejecting that metadata string alone. `Genome_genomeLoad:253–284` reserves larger G and SApass1/SApass2 buffers and points SA into their tails when insertion is enabled. Single-buffer substitution without this alias/epoch logic is incorrect. If a run requests dynamic SJ, second-pass mutation or sequence insertion, select stock CPU mode before publishing a GPU context. Any future support requires draining, mutating/rebuilding, revalidating and publishing a new epoch, then invalidating every table. Source index files must stay unchanged across both snapshot loads/validation; file-backed `map_file_unchecked` is not an immutable snapshot and is not the proposed loader.

## Proposed private C ABI — logical contract, no implementation

Existing baseline, not invented: `crates/umgpu/shim/seed_probe.cu:46` exports `umgpu_seed_probe(g,sa,reads,read_bytes,requests,start,n,config,out,stats,variant,event_ms,stream)`. Main Rust `cuda.rs:914–1087` declares it and wraps it in `seed_probe` / `seed_probe_variant`, checking ATS/context, leases, extents and output overlap, executing an optional scoped CPU callback, and synchronously draining the stream. This is a probe transport with caller-managed leases, **not** an opaque STAR integration context. C++ `seed_probe.h` itself uses C++ syntax; a true private C header would need C-compatible declarations.

Proposed names below do not exist. Use a versioned private header with fixed-width integer fields, 8-byte structure alignment, no C++ bool/enum/exception/Rust object across the boundary. Initial mode is synchronous; one coordinator serializes calls on one opaque context. No existing production ABI is changed.

| Proposed type | Exact logical layout |
|---|---|
| `UsiContext` | Opaque incomplete type, allocated and destroyed only by backend |
| `UsiIdentityV1` | Six u64 fields at offsets 0…40: genome_file_bytes, sa_file_bytes, sai_file_bytes, n_sa, strand_bit, sparse; then 96 bytes of binary SHA256 digests in Genome/SA/SAindex order at offset48; size144 |
| `UsiRequestV1` | Ten u64 fields at offsets 0,8,…72: tag, s0, s1, read_len, S, N, L_in, i1, i2, dirR; size80; same payload order as existing ProbeRequest |
| `UsiResultV1` | Five u64 at 0…32: L_out, low, high, count, status; size40, inclusive interval; result j corresponds to request j |
| `UsiBatchStatsV1` | Six u64 at 0…40: requested, gpu_ok, rejected, compared_bytes, sa_gathers, main_iterations; then four u64 nanosecond fields at48…72: materialize_ns, device_event_ns, device_call_ns, total_call_ns; size80 |
| `UsiErrorV1` | u32 code at0, u32 reserved=0 at4, char message[248] at8, NUL-terminated; size256; caller owns it |

Exact proposed signatures (declarations only):

```c
typedef struct UsiContext UsiContext;
int32_t usi_init_v1(const char *index_dir, const UsiIdentityV1 *identity,
                    uint64_t index_epoch, UsiContext **out, UsiErrorV1 *error);
int32_t usi_search_batch_v1(UsiContext *ctx, uint64_t index_epoch,
                    const uint8_t *reads, uint64_t read_bytes,
                    const UsiRequestV1 *requests, uint64_t n,
                    UsiResultV1 *results, UsiBatchStatsV1 *stats,
                    UsiErrorV1 *error);
int32_t usi_destroy_v1(UsiContext **ctx, UsiErrorV1 *error);
```

The type layouts in the table define the omitted struct declarations; this is not proposed source to compile on this card. Init copies the path/identity, validates the pinned profile and snapshots arrays into backend-owned buffers; `*out=NULL` on failure. Epoch must be nonzero and matches at every batch; it identifies loaded immutable content, not an unchecked caller permission to change arrays. ABI version is in symbols; no optional layout-size guessing. Identity's Genome file bytes determine nGenome; init validates packed lengths, strand32/sparse1 and disk metadata, including the 194-chromosome/SJ profile. No SAindex device pointer is needed. The allocator-patch alternative would require a separately reviewed private writable-allocation/freeze/view bridge; these duplicate-loader signatures do not pretend to expose it.

Request `tag=0` means inner search. `s0/s1` are byte offsets into the batch read arena, not host pointers; each names `read_len` valid numeric bytes. dirR=1 means forward; dirR=0 reverse; other values are rejected. The v1 GPU admission limit is `0 < read_len <= 4096`, matching the current probe transport rather than promising arbitrary read lengths. N>0, L_in≤N, i1≤i2<nSA; S and N must stay in the read bounds in the selected direction. All offset/addition/count multiplications are checked. Non-ACGT sentinels retain exact STAR representation; caller rejects unsupported semantic profiles to CPU, rather than remapping unsupported bytes. The CPU wrapper retains `(read_generation,ip,iFrag,istart,call_kind)` and the slot-to-consumer mapping; these are not kernel search inputs. It must compare the complete actual tuple with a table entry before use.

All arrays, path and error storage are borrowed only for the duration of the synchronous call. The backend copies/materializes caller reads and requests into its owned umem arena, freezes and leases them, uses disjoint output buffers, waits for completion, then copies results/stats back. It caches capacity across batches without retaining caller pointers. These copies and validation are included in materialize/total call timing; they were not all included in the warmed probe rate. The index buffers persist from init to destroy; request/read/result capacity persists internally but contents can be reused only after completion. Nonzero n requires all pointers and distinct writable result/stats/error storage; n=0 is a specified no-op with zero stats. A first cap of n≤1,000,000 is an integration contract choice within the current probe's ≤4M limit, not a tuning result.

Call return 0 means transport completed and all per-slot statuses are defined; nonzero means no results may be consumed. Suggested fixed codes: 1 bad ABI/input, 2 unsupported index/profile/epoch, 3 allocation/placement failure, 4 GPU failure, 5 uncertain completion. Per-result status 0 means usable tuple, 1 unsupported tag/domain, 2 invalid extent, 3 index/comparison bounds failure, 4 invalid result range. Do not conflate a rejected result with Nrep=0. Copy the detailed message into caller error storage; no borrowed last-error string. Catch backend exceptions/panics at the boundary. Destroy is null-safe, drains, frees confirmed-safe buffers and nulls the handle; uncertain device completion quarantines backend allocations rather than freeing memory the device may still touch, and reports code5. Caller storage remains safe because the device used internal owned materialization, not caller pointers.

On rejected slots or a failed batch, run the original CPU search with the **original** tuple before any storeAligns effects. Increment reasoned fallback counters and disable further GPU submissions on transport/index faults. An invalid-result/index-bounds error is visible as a backend defect, not silently treated as an ordinary off-grid miss. For an admission-profile mismatch, choose stock CPU mode from the outset. Do not “clamp” N or intervals to make a request fit. Ordinary off-grid fallback remains a valid expected policy. In parity runs, count any GPU-vs-stock mismatch as failure even if fallback preserves output; fallback is not a way to hide wrong answers.

Report counters for actual outer/inner calls, submitted/unique candidates, consumed table hits, unused results, off-grid misses, exact-key mismatches, rejected slots by reason, whole-batch failures and CPU fallback calls. Count prefix and table CPU time, main versus expansion loops and logical comparison bytes separately where available. Existing ProbeStats.loops includes both main and expansion loops, whereas SPLIT iterations includes only main; `main_iterations` above requires a deliberately separate counter and cannot be populated by relabeling ProbeStats.loops. Detailed 48-byte per-request probe stats can remain a diagnostic mode; aggregate production stats must state their overhead. Export integration timings/counters in a clearly named new section of Log.final.out; existing stock mapping fields remain unchanged.

An asynchronous API is **deferred**, not hidden in this synchronous contract. If later necessary, it needs an opaque submission owning input/read/output/index leases, explicit poll/wait and result retrieval, and teardown that drains or quarantines. Caller memory must remain owned or be copied before submit returns. Twenty synchronous caller threads are not an asynchronous scheduler; one synchronous coordinator can still service large lookahead windows while CPU workers do independent work. Do not expand the held owned-session work before REAL-REQUESTS.

## Correctness and conditional decision

Default CPU fallback is the correctness baseline. The GPU returns only a pure inner tuple. CPU prefix/short/direct processing, sparse winner selection, PC insertion, seed-window construction, stitching, selection, filters, SAM tags and output remain stock. Unsupported initial profiles/remaps bypass GPU. Stock 20M and 5M evidence establishes the counters boundary's mapping parity, not the probe kernel's upstream correctness.

Require exact captured STAR `(L_out,low,high,count)` agreement for the measured request domain, then, **after implementation is authorized**, exact stock SAM biological records **including record order and all tags**, exact SJ output and existing non-timing Log.final.out fields on the agreed input/profile. Normalize only approved executable/output-prefix fields in command headers and approved timing fields; do not sort away order differences, remove tags, broaden header normalization or accept mapping-rate agreement. New integration telemetry is compared separately, never used to relax stock fields. Preserve chunk assignment and worker RNG sequencing; if those change despite identical record order, prove stock parity rather than assuming it.

Decision criteria after REAL-REQUESTS:

- **≥5×, correct real tuples:** retain thread GPU and evaluate (a)'s measured work coverage and full preparation/materialization budget. If initial starts cover enough expensive work and unused work is modest, authorize a small private integration experiment separately. The N peaks motivate this choice but do not establish it.
- **Approximately 2×:** present real time saved and overhead/coverage estimates for a user decision. Do not automatically resume old cards or invoke the synthetic 10.21× result to override it.
- **Weak or negative real result / tuple mismatch:** do not implement integration on this evidence. Preserve the distinction between a performance failure and a correctness/domain issue for the user's decision.
- **Strong real speed, poor initial coverage:** compare (c) candidate work against additional CPU cost covered; select added grid positions only if measured `G+H<U`. If adaptive requests carry most cost and grid waste is high, (b) may be justified, but only with compact continuation-memory and enough-ready-reads estimates. It is not the first patch by default.

No whole-STAR speedup can be computed from SPLIT bytes. Even the earlier 39.03% seeding CPU bracket is broader than the inner boundary. CPU-s savings, STAR wall reduction and pipeline CPU-min/sample are different outcomes. The old roadmap's numerical integration reduction is a later measured objective, not proof furnished by synthetic replay.

One independent read-only review pass checked this design against the pinned source, raw SPLIT evidence and current APIs. It found no blocking issue; its fixed-length-default and synthetic-interval wording corrections, plus explicit ABI admission limits, are incorporated. No implementation was tested or authorized.

## Implementation on-ramp after the decision

After an affirmative REAL-REQUESTS decision **and explicit implementation authorization**, freeze the measured request/result contract and source/index identity. Implement one private compile-flag path: duplicate G/SA context, synchronous batch bridge, CPU prefix preparation, bounded initial-start window, exact tuple lookup, and CPU fallback; retain the original function as oracle and fallback. Keep existing per-worker downstream workspaces, stock read/chunk/RNG ownership and ordered result consumption. Measure the real 64k and 256k window cost including candidate construction, unused searches, read/request materialization, lookup and fallback. Run the agreed exact SAM/order/tag/SJ comparison once against stock and report both CPU-s and wall/RSS/startup changes. Use that concrete result to choose whether to stop, expand a measured grid, implement continuations, or justify the allocator ownership patch. This is an on-ramp for a later authorized experiment, not authorization or a revived hardening ladder.
