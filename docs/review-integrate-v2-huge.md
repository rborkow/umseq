# P2C-INTEGRATE-V2-HUGE-REVIEW

## Verdict

**Credible with caveats as a measured binary comparison; not yet credible as “MADV_HUGEPAGE alone saves 12.3%,” or as a portable STAR speedup.** The nine raw rows reproduce a 92.67 CPU-second (12.281%) reduction from stock to bypass, with a remarkably consistent 80.09-second user-time reduction. Huge pages are a plausible contributor of this magnitude. However, bypass also changes file-cache policy and contains integration hooks; stock and bypass page residency were not established by the supplied timing evidence. The proposed 1.28-billion-gather denominator contradicts the supplied sidecar, and the blanket “TLB-bound; 2 MB pages fix it” explanation exceeds the evidence. Publish the observation only with these qualifications until a same-build advice ablation establishes causality. Treat it as a GB10/configuration/sample-specific result, with applicability to Batch unresolved.

## Blocking

- **Separate advice from eviction and hooks.** Compare the Round 7 bypass build against an otherwise identical build with only the huge-page advice disabled, retaining `fadvise` and all hooks. Equalize cache state before each run and verify that the intervention actually changes index page backing. Reproduce at 20M and 20 threads with rotated repeats before attributing the quoted percentage to advice. A short run is a disqualifier, not a replacement for this measurement.
- **Establish the actual stock and bypass baseline.** Record page policy, kernel/base-page size, allocator version/configuration, executable provenance, and index-address-specific `smaps` during mapping in both arms. The supplied `index_anon_huge_bytes=30175920128` establishes reported coverage in GPU repeat 1, not in either CPU arm. Already-huge stock would invalidate the asserted 4 KB-versus-2 MB contrast, though it would not erase the observed binary difference.
- **Correct the work denominator before publishing the mechanism.** `gathers_hit` is **3,194,350,096**, not approximately 1.28 billion. It is a consumed-work counter, not measured CPU TLB misses or necessarily unique GPU work. Explain its relation to stock execution before extrapolating it to all CPU seed searches.
- **For a memo claiming general or AWS Batch savings, measure the actual deployment.** A GB10-only memo can proceed after the above with explicit scope. An x86 claim needs stock residency and a controlled timing comparison on the relevant AMI/container/instance. Neither an architecture name nor a distribution default establishes residency.

## Should fix

- Replace the Round 7 table's description “stock + MADV_HUGEPAGE” with “integration bypass + allocation advice + index-cache eviction.” The generator applies advice to `PackedArray::allocateArray` generally, not exclusively the three named index allocations.
- Do not subtract the historical +1.8% hook floor as if it were measured in Round 7. Page size can change the relative floor, and code generation, hook placement, and build provenance can change it independently.
- The checked-in Round 7 **Open** section mentions cache carryover but does **not** explicitly request the compiled-out-`madvise` split described in the review prompt. Agree with that proposed split; do not attribute text to the bench document that is absent from this checkout.
- In [round7_followup.sh](../bench/star-integrate/round7_followup.sh), `$!` belongs to the background `env … /usr/bin/time … STAR` command. After `env` execs, this is normally the **time parent**, not STAR. Resolve the STAR child and verify `/proc/<pid>/exe` and `cmdline` before sampling; otherwise a near-zero `AnonHugePages` result is misleading. Its warm/cold bypass experiment leaves both advice and eviction enabled and therefore does not isolate the two patches. Also explicitly unset `STAR_INTEGRATE` for CPU arms; an empty `env` argument list does not remove inherited variables.
- The same script classifies kernel samples by symbol-name substrings and labels unknown addresses kernel. That is not reliable evidence for +43 seconds of kernel execution. Use perf's recorded privilege context/DSO and report unresolved samples separately. Retain real per-thread stacks and stage attribution.
- Record `madvise`/`posix_fadvise` return values in a diagnostic run. Advice is currently unchecked. Hard-coded 4096-byte rounding is valid only for an appropriate base-page configuration; on a 64 KB kernel it can produce an invalid start address. A successful call still does not guarantee huge-page allocation.
- Preserve the actual command lines, hashes, build flags, cache preparation, affinity, frequency/thermal state, cgroup limits and parity evidence with the next measurement. Do not turn STAR process CPU-seconds into saturated-box throughput or the repository's Rust-control cost comparison. Background reclaim/compaction and I/O workers can consume CPU outside the timed process.

## Answers

### 1. Mechanism and arithmetic

Evidence read first: [Round 7](../bench/PHASE2C-integrate-1.md#round-7-integrate-v2-t5c--coordinator-fixes-92471bfhead-borrowed-index-gate-passed-first-valid-whole-chain-timing), [raw timings](../bench/evidence/integrate-1-host/timing-round7-raw.tsv), and [GPU repeat-1 stats](../bench/evidence/integrate-1-host/timing-round7-r1-gpu-stats.jsonl). These are the supplied measurements; no new performance experiment was run for this review.

| Repeat | Stock user/sys | Bypass user/sys | GPU user/sys |
|---|---:|---:|---:|
| 1 | 725.20 / 27.09 | 643.75 / 18.43 | 591.86 / 62.34 |
| 2 | 722.15 / 35.20 | 643.69 / 17.36 | 591.53 / 64.59 |
| 3 | 721.91 / 32.16 | 641.55 / 20.92 | 594.62 / 59.24 |
| Mean | 723.0867 / 31.4833 | 642.9967 / 18.9033 | 592.6700 / 62.0567 |

All values are seconds. Stock mean total is 754.57, bypass 661.90, GPU 654.7267. Thus `(754.57 − 661.90) / 754.57 = 12.2812%`. User savings are 80.09 seconds; sys savings are 12.58 seconds. These sums do not establish which stage saved them.

GB10 is not a homogeneous Neoverse machine: NVIDIA specifies **10 Cortex-X925 and 10 Cortex-A725** cores ([Spark hardware](https://docs.nvidia.com/dgx/dgx-spark/hardware.html)). The [Cortex-X925 TRM, table 5-1](https://documentation-service.arm.com/static/68374ea93f2acc596c2d9d93) specifies a 96-entry fully associative L1 data TLB and a shared instruction/data, 8-way, 2048-entry L2 TLB supporting 4 KB and 2 MB translations. Intermediate walk entries also use that L2. I did not establish the A725 geometry here; applying the following X925 approximation to all 20 threads is a model assumption, not a hardware measurement.

**Capacity model, explicitly hypothetical:** use 30 GiB to make the approximate index arithmetic transparent; the sidecar's actual reported huge coverage is 30.176 decimal GB (28.104 GiB). With an ideal 2048-entry translation cache and uniform independent accesses:

| Quantity | 4 KiB | 2 MiB |
|---|---:|---:|
| Pages in 30 GiB | 7,864,320 | 15,360 |
| 2048-entry reach | 8 MiB | 4 GiB |
| Ideal hit fraction | 0.0260% | 13.3333% |
| Ideal miss fraction | 99.9740% | 86.6667% |

Even huge pages leave most uniform-random translations missing. For a 24 GiB SA alone, reach fractions are 0.0326% and 16.67%; a 3 GiB genome has 1,536 huge pages and could fit in an otherwise empty L2 TLB, but it competes with SA, SAindex, instructions, and walk entries. Per-core reach cannot simply be multiplied by 20: cores perform overlapping searches. Real prefix-restricted binary searches have locality, and byte comparisons usually stay within one genome page. Neither every byte nor every gather necessarily incurs an independent walk.

Let `N` be comparison/SA-gather opportunities, `k` the effective number of random translations per opportunity, `m4/m2` miss probabilities, and `w4/w2` exposed walk penalties. Then an illustrative mapping-user-time reduction is:

`ΔU ≈ N × k × (m4 × w4 − m2 × w2)`.

This estimates exposed CPU stall time, not raw memory latency: overlap, page-walk caches and scheduling matter. It is already aggregate CPU time; **do not multiply by 20 again**. For an SA plus genome lookup, `k` may approach two, but can be smaller because of empty comparisons and reuse; SAindex accesses are additional work.

The sidecar has `compared_bytes_hit=16,688,121,129`, `gathers_hit=3,194,350,096`: **5.224 compared bytes per gather**. It reports 194,589,601 consumed chain steps, about 16.42 gathers per chain step. The local [ProbeSearchImpl::compare](../crates/umgpu/shim/seed_probe.h) increments `gathers` once per comparator/SA fetch, including an empty comparison. It is not a hardware-load or TLB-event count. `submitted_stats.gathers=2,004,628,078` is lower than consumed gathers; consumption can count reused results. The integration accumulation must be reconciled against CPU work, not silently replaced by a smaller denominator. Unused GPU work and CPU fallbacks further prevent treating this as the exact stock total.

Using the supplied hit count as a conditional CPU-work proxy, the observed user difference requires `80.09 / 3.194350096e9 = 25.07 ns` saved per gather (about 412 ns per consumed chain step). Assigning the entire user+sys difference to gathers would require 29.01 ns, but wrongly conflates hardware walks with kernel allocation/I/O work. Using the prompt's unsupported 1.28 billion instead requires 62.57 ns user or 72.40 ns total per gather.

For illustration, **assume**, do not claim measured, exposed penalties `w4=100 ns`, `w2=87 ns`, `k=1`. The table's miss fractions yield `99.974 − 75.400 = 24.574 ns` per opportunity, or **78.50 modeled CPU-seconds** over 3.194 billion opportunities. Per chain step that is roughly 404 ns. Alternatively, if `w4=w2=100 ns`, improved hit rate alone saves 13.307 ns per translation; two independent translations give about 85.01 modeled CPU-seconds. With 1.28 billion opportunities, equal-cost walks would instead need approximately 470 ns per walk at `k=1`, or 235 ns at `k=2`, to explain 80.09 seconds. These are sensitivity calculations, not benchmark results or fitted proof.

The magnitude is therefore plausible but does not uniquely fall out of the model. Huge mappings can both improve reach and shorten/cache walks. For 30 GiB, eight-byte final descriptors occupy roughly 60 MiB at 4 KiB versus 120 KiB at 2 MiB: a large reduction in descriptor footprint even when huge-page TLB misses persist. Linux documents both faster misses and improved TLB coverage, as well as fewer first-touch faults ([THP documentation](https://docs.kernel.org/admin-guide/mm/transhuge.html)). The 12.58-second sys decrease could include fewer faults and cheaper allocation/teardown; it is not evidence that user-mode page walks entered the kernel. Obtain mapping-phase PMU evidence before saying “TLB-bound.”

If the old +1.8% floor were unchanged, the hypothetical no-advice bypass would be `754.57 × 1.018 = 768.1523` seconds. Its difference from 661.90 is 106.2523 seconds: **14.081 percentage points of stock**, or **13.832% of that hypothetical bypass baseline**. Neither is a measured page-only saving. “About 14%” must retain both the assumption and denominator.

### 2. Prior art

**STAR-specific controlled THP timing: none known to me, and none verified in this search.** This is not a novelty proof. There is relevant BWA prior art: Estrada et al., *Performance Comparison and Tuning of Virtual Machines For Sequence Alignment Software* (2015), study BWA/Novoalign virtualization; indexed full-text evidence identifies a ten-sample BWA chr1 comparison including KVM THP tuning ([publisher article](https://www.scpe.org/index.php/scpe/article/view/1061), [paper](https://www.scpe.org/index.php/scpe/article/download/1061/428/0)). Full PDF retrieval failed in this review, so I do not quote a THP speedup or claim it isolates guest index pages. Host huge pages can improve nested translation independently of guest page size.

A search hit linking Bowtie and huge pages in a [PRACE container/VM report](https://prace-ri.eu/wp-content/uploads/WP286.pdf) is not such evidence: its Bowtie experiment concerns container overhead, while the huge-page statement concerns separate PCOCC VM benchmarks. BWA's FM-index and STAR's suffix array have related translation-pressure risks, not interchangeable footprints or locality.

### 3. Confounds and allocation paths

**(a) Stock THP is an empirical question.** I checked the upstream **2.7.11b-tagged source online**, rather than citing the full source from memory; this checkout's `docs/tool-src/` inventory does not contain STAR excerpts. `Genome::genomeLoad` uses `new char[]` and packed-array allocations for `NoSharedMemory`, then reads the files into those arrays ([Genome_genomeLoad.cpp](https://raw.githubusercontent.com/alexdobin/STAR/2.7.11b/source/Genome_genomeLoad.cpp)). `PackedArray::allocateArray` itself just allocates the byte array ([PackedArray.cpp](https://raw.githubusercontent.com/alexdobin/STAR/2.7.11b/source/PackedArray.cpp)). These paths contain no huge-page advice. Large allocations through ordinary glibc normally become anonymous mappings; file-cache backing and these anonymous index arrays are distinct.

Under `madvise`, a conventional allocator without advice should leave those arrays on base pages. But **unset `GLIBC_TUNABLES` is insufficient proof**: the [current glibc manual](https://sourceware.org/glibc/manual/latest/html_node/Memory-Allocation-Tunables.html) describes `glibc.malloc.hugetlb=1` as requesting `MADV_HUGEPAGE`, `2` as explicit HugeTLB, and now documents an AArch64 default of 1. That current default must not be projected backward onto the measurement host's installed libc. Identify its version and downstream patches. Check `GLIBC_TUNABLES`, `LD_PRELOAD`, alternative allocators, launcher scripts and any `MALLOC_HUGETLB` setting; the latter is not a substitute for verifying the documented glibc tunable and actual allocator behavior.

On the box record `getconf PAGESIZE`, `uname -r`, `ldd --version`, THP `enabled`, `defrag`, `hpage_pmd_size`, per-size `hugepages-*kB/enabled`, and the relevant environment of the actual STAR process (avoid dumping unrelated secrets). Inspect `/proc/<STAR-pid>/smaps_rollup` once after load and its index VMAs in `smaps`: addresses, `AnonHugePages`, `VmFlags` (`hg`/`nh`), `THPeligible`, page-size fields and explicit HugeTLB accounting where available. `hg` means advised, not resident; rollup can include unrelated huge allocations. Check `THP_enabled` in process status when available. Policy and page-size fields alone do not establish every mapping's backing. Modern per-size settings can override the top-level policy; process-level disablement can prevent THP ([kernel controls](https://docs.kernel.org/admin-guide/mm/transhuge.html)).

**(b) Eviction can move CPU-seconds, not merely wall time.** `POSIX_FADV_DONTNEED` attempts to release cached file pages; it is advisory, and errors are ignored here ([Linux API specification](https://man7.org/linux/man-pages/man2/posix_fadvise.2.html)). The generator actually drops all three files together after `SAiIn.close()`, not separately immediately after each individual read. Eviction work can increase the patched process's own sys time. A following cold reader can pay filesystem, readahead, page-cache allocation and I/O submission CPU; pure disk wait is not CPU time, and some work is charged to kernel workers. Freeing cache can also reduce later reclaim pressure, so the net direction is not guaranteed.

The stated rotation balances positions, **not predecessor cache treatment**. Assuming no intervening preparation, sequence is `S B G | G S B | B G S`. Both later stock runs follow GPU eviction; bypass is warm after stock twice and cold after bypass once; GPU follows an evicting arm every time. Stock sys is 27.09/35.20/32.16; bypass sys is 18.43/17.36/20.92. Wall rows reinforce the association: bypass 43.73/42.17/65.87 versus stock 56.08/70.98/71.25. This biases the comparison in bypass's favor if cold-read sys costs dominate. It does not explain away a stable ~80-second user gap, but neither do these rows partition the 12.58-second sys gap. A `flock` does not control cache history, allocator state, background daemons or heterogeneous-core scheduling.

**(c) Shared-memory modes are outside the demonstrated allocation intervention.** In the checked tag, `LoadAndKeep`, `LoadAndRemove`, and `LoadAndExit` use `SharedMemory::Allocate/GetMapped`; G points into that segment and SA/SAi use `pointArray`. They bypass the private index `new[]` sites. Attaching to an existing segment also bypasses the file reads. The post-close file eviction is outside the read conditional and can still run. Shared-memory THP policy (`shmem_enabled` and backing-specific settings) and the creator's allocation history need their own inspection. This result applies to the tested private-load path, not automatically to a cluster keeping a shared index resident across samples ([tagged allocation branches](https://raw.githubusercontent.com/alexdobin/STAR/2.7.11b/source/Genome_genomeLoad.cpp)).

### 4. Portability

**Do not assert that AL2 and AL2023 both default to `always`.** My recollection of AL2 is moderately confident, but I did not verify a first-party Amazon default statement for both distributions; confidence in the joint claim is low. AWS's [performance runbook](https://github.com/aws/aws-graviton-getting-started/blob/main/perfrunbook/optimization_recommendation.md) presents `always` and `madvise` as configuration choices, not proof of the team's current AMI state. Read the actual host controls. A Batch container supplies userspace, not an independent host-kernel THP policy. Instance family alone is not enough.

If x86 stock already has near-full index THP coverage **during mapping**, the marginal benefit of explicit advice could approach zero; the source patch would then mostly address a configuration deficit on the workstation. Even `always` does not guarantee identical treatment: defrag policy can distinguish advised allocations, and fragmentation/promotion timing can differ. An x86 VM also has host-side translation effects unavailable to guest `smaps`. This result is currently workstation-specific evidence, not proof that it is intrinsically workstation-only.

The cheapest x86 check is one stock run through index loading and a small mapping prefix, reading the true STAR PID's index `smaps` plus kernel policy. Near-full THP immediately weakens the projected Batch opportunity; near-zero coverage keeps it open. This settles residency, **not speedup**. Follow with an advice-only A/B timing if a deployment claim is needed. `perf stat -e dTLB-load-misses` alone cannot identify backing page size and may count L1 misses satisfied by another TLB; choose the actual CPU's completed-walk/walk-cycle events via `perf list` and its PMU documentation.

### 5. Cheapest falsifier

**The best single causal measurement is a paired bypass timing with only the `madvise` intervention removed, leaving `fadvise` and hooks in place.** Use equal cache preparation, full index, same input and threads; verify base-page residency in the off condition and huge residency in the on condition. If the off condition retains essentially the same saving, attributing the 12.3% to advice is falsified. A partial loss measures a smaller contribution or interaction; disappearance of the saving supports, but does not precisely quantify from one pair, the page explanation. If both conditions still get THP, the ablation did not test the hypothesis.

This is the right split proposed in the prompt. An available process wrapper that sets `PR_SET_THP_DISABLE=1` before exec can provide an even cheaper no-rebuild disqualifier on the existing bypass binary, but affects **all** allocations rather than just the patched sites. Conversely, `PR_SET_THP_DISABLE=0` does **not** force `THP=always`; it merely removes the per-process prohibition and leaves kernel policy/advice effective ([prctl behavior](https://docs.kernel.org/admin-guide/mm/transhuge.html)). A preload advising large mappings, or supported `glibc.malloc.hugetlb=1` on stock, is useful corroboration, but broader than an index-only change and must be verified. Do not change the whole host's policy merely to avoid making the controlled variant.

### 6. GPU interpretation and ATS

The observed increment remains `(654.7267 / 661.90 − 1) × 100 = −1.08375%`: **7.1733 seconds saved, comprising 50.3267 seconds less user and 43.1533 seconds more sys**. Relabeling bypass does not alter arithmetic. It becomes “GPU versus this integration-bypass memory/cache configuration,” not an established increment over optimally configured stock. Both arms evict files, but their predecessor histories differ; the small net difference is particularly exposed to startup/sys confounding. Against a newly measured fair CPU baseline `C`, the result is `100 × (654.7267/C − 1)` only if the GPU total is still comparable under that protocol. There is no defensible corrected numeric percentage yet, and no x86 GPU result follows from a GB10 experiment.

NVIDIA documents ATS sharing a process's host page tables on Grace Hopper/Grace Blackwell, and `cudaDevAttrPageableMemoryAccessUsesHostPageTables=1` as the capability check; ATS replaces the HMM software-coherency path when available ([CUDA memory guide](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/understanding-memory.html), [Grace Hopper architecture](https://developer.nvidia.com/blog/nvidia-grace-hopper-superchip-architecture-in-depth/)). NVIDIA's [Warp hardware-coherency design](https://github.com/NVIDIA/warp/blob/main/design/hardware-coherent-memory-access.md) includes DGX Spark among ATS platforms. Capture the capability/driver addressing mode on the actual box.

Shared page tables do not mean a shared CPU/GPU TLB. Grace documentation describes an **ATS translation buffer unit**, a distinct translation path ([Grace tuning guide](https://docs.nvidia.com/grace-performance-tuning-guide.pdf)). Larger host mappings can reduce translation demand and walk depth, but this does not establish GB10 GPU cache capacity, cached translation granularity, or equal CPU/GPU benefits. I have not verified those GB10-specific details. A 2 MB mapping on a 4 KB kernel is normally a block/PMD-level descriptor, not literally a giant last-level PTE; on other base-page configurations, physical folio size and translation size can differ.

**An ordinary hardware ATS/TLB miss is not a Linux system call and does not automatically charge STAR sys time.** Fault handling, mapping/invalidation, driver work, memory accounting and synchronization can produce sys time; translation-cache thrashing itself can stall GPU execution without it. Thus +43 seconds is compatible with some driver/VM explanation, but is not affirmative evidence of “page-table work from ATS access to 2 MB pages.” It is also compatible with buffer allocation/teardown, procfs walks and other kernel work. A userspace synchronization spin would ordinarily increase user time, not sys. Attribute real stacks by stage and thread before blaming ATS or subtracting 43 seconds from a hypothetical future GPU result. The 0.343-second setup wall measurement does not rule out mapping-time or teardown kernel costs.

## Suggested measurements

Ordered by cost; all are proposals for the orchestrator, not measurements performed by this review. Retain raw rows, environment and evidence directory, run one heavy job under the resource lock with an absolute timeout, and avoid broad host cache/policy changes.

1. **Existing artifact/environment audit and one correctly targeted residency snapshot per CPU arm.** Record executable/libc identity, relevant environment, base-page and THP settings; verify PID via `exe`, then capture index `smaps` after load. Use a currently running matching process if available, otherwise a short full-index run. Stock already huge or bypass not huge disproves the assumed page contrast; neither outcome alone disproves the timing difference. Repeat this cheap stock observation on the actual Batch x86 configuration when accessible.
2. **One short full-index ablation pair**, same bypass build except advice disabled, eviction retained, identical warm-cache preparation outside timing and verified page contrast. If an existing THP-disable exec wrapper is available, use it first as a broader cheap disqualifier. No user-time regression with verified base pages defeats the dominant page explanation. A regression warrants the full experiment; short-run percentages must not be extrapolated because loading/teardown are fixed costs.
3. **Three rotated 20M ablation repeats**, 20 threads, same build options and controlled cache state. Preserve total user/sys, mapping-stage CPU from defensible stage boundaries, faults, and page backing. The advice-only difference is the publishable causal estimate within this bypass configuration. Keep output parity gates unchanged and verify exact required artifacts; exit code zero is not output identity.
4. **Stock plus only huge-page advice versus stock**, under the same protocol, followed by a cache-policy 2×2 only if needed. This tests whether the hook floor changed and whether a minimal stock patch reproduces the gain. Holding page policy fixed while toggling eviction measures eviction's direct cost and memory-pressure interaction. Warm/cold runs diagnose carryover but do not replace this split. Repeat the minimal A/B on the deployment x86 host before making a portable numerical claim.
5. **Mapping-phase CPU PMU profile of the CPU pair, and per-thread user/kernel profile of GPU versus bypass.** Use validated architecture-specific L2 refill/walk events and cycles/instructions on both GB10 core types; keep event counts and privilege modes. Fewer exposed walk stalls with similar work supports the mechanism; unchanged walk behavior points elsewhere. Resolve +43 seconds into load, mapping and teardown stacks. If generic perf events are unsupported or ambiguous, report that rather than naming them TLB walks. Saturated-box cost/throughput is a subsequent experiment, not a conversion of these single-process totals.
