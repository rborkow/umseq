## Concern: the rigor is being spent ahead of the evidence that would justify it

Since the CPU-accounting result, no measurement has moved the actual question — *can GB10's
GPU beat 20 cores on this access pattern over the real 30 GB index?* — by any amount. What
was built is correctness infrastructure for an inner boundary whose share of the 39% is
itself unmeasured, and whose GPU viability is unknown. Two specific issues:

**(a) The inner boundary's share of the seed cost is unknown, and the instrument to measure
it already exists.** `ReadAlign_maxMappableLength2strands.cpp:80–89` (direct unique-hit
extension) and `90–96` (inner search) both call `compareSeqToGenome`; the `perf` self-time on
`compareSeqToGenome` (25–34%) is the sum over both. Only the inner path is replayed. If most
real-index requests resolve on the direct path (plausible: `genomeSAindexNbases=14` gives a
prefix lookup that often lands a unique hit), the replay boundary covers a minority of the
39%. The capture hooks already emit `direct_calls`/`direct_bytes`/`short_direct_inner` per
read — running the capture build on the real 20M input with **counters only, no trace
records**, gives the inner/direct/short split and compared-byte totals in one Spark slot.
This should precede P2C-REPLAY-SCALE, because it decides whether scaling *this* boundary is
worth it or whether the boundary must widen to include direct extension.

**(b) The GPU viability question is being deferred behind a correctness ladder that is a
week long at this rigor.** The plan's sequence — PE coverage → missing branches → full-index
capacity → real-data replay → CPU replay profile → *then* conditional CUDA — is right for
shipping. It's wrong for *deciding whether to ship*, because the kernel's odds are ~45% and
every rung costs a day. The plan's own risk #1 ("a random-gather microbenchmark is not a
suffix search") cuts both ways: if the GPU can't beat 20 cores on the *easier* problem, it
won't on the harder one. That upper bound is cheap and is exactly the T6-style measurement
this project exists to make.

## Recommendation

Hold **P2C-REPLAY-SCALE**. Two cards instead, in parallel, one Spark slot each:

1. **P2C-SEED-SPLIT** (Terra, tooling): capture build in counters-only mode on the real
   ERR188140_20M / full-index run. Report: inner vs direct vs short-shortcut request counts,
   compared bytes per path, per-direction breakdown, and CPU-s attribution if the hooks can
   cheaply timestamp (they may not — counts are enough). One run, three repeats not needed.
   Output decides the boundary: inner-only if ≥70% of compared bytes; otherwise inner +
   direct extension (still a pure function of `(s, S, N, a, dirR)`, so replayable).

2. **P2C-SEED-GPU-PROBE** (Terra, performance-only, explicitly *not* a correctness gate):
   load the real packed SA + genome + SAindex through `umem` (THP, no register); implement
   the lane's `search.cpp` algorithm as one-request-per-thread CUDA in a new
   `crates/umgpu/shim/seed_probe.cu`; drive it with *synthetic* requests drawn from real
   read bytes (the lane's `make_capture.py` machinery can emit them, or sample 20-mers from
   the FASTQ). CPU control = the lane's own independent `search.cpp` under OpenMP on 20
   cores, same requests, same resident index. Gate: GPU and CPU replay agree on every tuple
   (they're the same algorithm, so this is a smoke test, not the oracle); report
   requests/s at batch 4k/16k/64k, achieved GB/s, THP coverage, and divergence stats
   (mean/max `compareSeqToGenome` length per warp). **Decision rule: <1.5× over 20-core CPU
   at any batch size → park the lane, publish the negative; ≥2× → fund REPLAY-SCALE and the
   real kernel card at full rigor.**

Card 2 reuses the lane's search as the CPU control, so the lane's correctness work is not
wasted — it becomes the spec. Nothing from card 2 goes near the correctness ladder; it lives
in `crates/umgpu` behind a feature flag and is labeled a probe in every artifact.
